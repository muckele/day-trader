## Wire format and digests

`manifest.schema.json` is an M1 descriptor document, not a claim of generic JSON Schema support. Its exact top-level fields are `schemaVersion: 1`, `maxBytes: 65536`, `maxDepth: 8`, `definitions`, `inputManifest`, and `applianceManifest`; the last two contain M1 descriptors. Trusted schema bytes are loaded from the deterministic source-relative path for this offline milestone; immutable packaged delivery remains deferred.

All data objects have exact required fields: no optional fields, extensions, nulls or unknown keys. Empty arrays represent absent optional payload members; omission is forbidden. JSON must be strict UTF-8 with no duplicate decoded keys, no exponent/fraction, negative zero, nonfinite numbers, booleans as integers, or integers outside the M1 safe range. Maximum wire size is 65536 bytes and container depth 8. All data strings are printable ASCII, bounded as specified below, preventing Unicode canonical divergence. Object keys are lexicographically sorted, arrays retain order, no insignificant whitespace, no slash escaping. Collections whose order is semantically irrelevant must already be sorted by ID and unique. Both runtimes reuse M1 scanner/check/encoder primitives; no permissive JSON decoder admission path.

Every `sha256` is exactly 64 lowercase hex characters over exact artifact bytes; `sizeBytes` is their exact byte length, positive and at most 68719476736 (64 GiB). Hashes are computed from small explicit synthetic bytes in tests, never invented Ubuntu/runtime hashes. `inputsDigest` is SHA-256 of the canonical complete ASSEMBLY_INPUTS document. `manifestDigest` is the API-returned SHA-256 of the canonical complete APPLIANCE_MANIFEST document and is **not a field in either document**. Detached future signatures will cover `acceptance:appliance:v1\0` followed by canonical output bytes, but no signing/envelope implementation or signature is generated by M3. The independent expected manifest digest is supplied separately by the consumer's approved input context; comparing a digest to a value read from that same manifest proves nothing. Neither digest establishes signer trust.

Paths on the host never appear in portable identity documents. Input/output location maps associate artifact/tool IDs with explicitly supplied local paths and are checked for exact ID membership. Guest installation paths are fixed policy, not caller file locations. A pathname is never evidence that its current bytes match the identity. Validation/consumption uses checked private snapshots or retained verified handles, with checks around copying/consumption; a post-validation substitution fails or cannot affect consumed bytes. Native runtime attachment must retain/recheck artifact identity at use, not reopen an unchecked pathname.

## Common records

Artifact identity fields, all required: `id`, `sha256`, `sizeBytes`, `version`, `sourceId`. `version` and `sourceId` are nonempty ASCII `[A-Za-z0-9._:+-]`, maximum 128 bytes; `id` belongs to the finite sets below. `sourceId` identifies independently reviewed provenance; it is not approval or a downloadable URL. No URL fetcher exists. Tool identity has the same fields with `id: "mke2fs"`; exactly one such tool is supplied, pinned by hash/version/size. Its local path is out of band and its observed bytes must match before use. Host architecture/venue approval is independent from these declarations.

Both documents require `manifestVersion: 1`, `architecture: "aarch64"`, `distribution: "ubuntu-24.04"`, `policy`, `payloadState: "INCOMPLETE"|"COMPLETE"`, and `missingPayload` (sorted unique IDs from the payload set). COMPLETE requires all payload IDs and an empty missing list; INCOMPLETE requires exactly the complement of supplied payload IDs and a nonempty missing list. Completeness is bookkeeping, not qualification. A synthetic fixture may represent complete synthetic payload for negative admission tests, but cannot qualify it.

Base input IDs, each exactly once: `rootfs`, `kernel`, `initramfs`, `kernelConfig`, `node`, `python`, `playwright`, `chromium`, `hostLauncher`, `hostBroker`, `contracts`. Payload IDs, zero or one each: `guestBootstrap`, `controller`, `proxy`, `verifier`, `rolePolicy`, `seccompPolicy`, `routePolicy`, `guestProbes`. No unknown artifacts, duplicate IDs or unpinned browser/runtime permitted. Missing future payloads are explicitly represented, never filled by implementing Tasks8 onward.

`policy` has exactly `layout`, `roles`, `devices`, `storage`, `resources`, `runtime`, `kernelFeatures`, `compatibility`.

* `layout` exact fields/constants: `guest: /opt/acceptance/guest`, `contracts: /opt/acceptance/contracts`, `nodeModules: /opt/acceptance/node_modules`, `probes: /opt/acceptance/tests/guest`, `bootstrap: /opt/acceptance/guest/confinement.py`, `controllerRoot: /run/acceptance/controller`, `browserRoot: /run/acceptance/browser`, `verifierRoot: /run/acceptance/verifier`, `proxyRoot: /run/acceptance/proxy`. These do not authorize a post-start arbitrary path/exec RPC.
* `roles` exact fields/constants: `controller: 10001`, `browser: 10002`, `verifier: 10003`, `proxy: 10004`. Runtime admission separately proves nonroot credentials/empty capabilities, inherited confinement, private directories and descriptor separation.
* `devices` exact fields/constants: `bootLoader: LINUX`, `baseBlock: VIRTIO_READ_ONLY`, `entropy: 1`, `serial: 1`, `serialAttachment: PRIVATE_PIPE`, `vsock: 1`, `vsockHostCID: 2`, `vsockPort: 4050`, `network: 0`, `networkAttachments: 0`, `shares: 0`, `usb: 0`, `audio: 0`, `graphics: 0`, `input: 0`, `balloon: 0`, `extra: 0`, `hostTCPAdmin: 0`. Every implicit/native extra device is rejected. Serial handles never default to raw stdin/stdout and never enter the broker. A vsock configuration is not a live listener.

## Input versus assembled output

ASSEMBLY_INPUTS exact top-level fields: common fields above plus `kind: "ASSEMBLY_INPUTS"`, `artifacts` (sorted identities, 11..19), `tools` (the one mke2fs identity), and `provenance`. Input provenance has exact fields `sourceRevision` (40 lowercase hex), `approvalId`, `buildEnvironmentId` (same ASCII identifier rule/max128), `inputClass: "SYNTHETIC"|"APPROVED_CANDIDATE"`. The latter is a declaration only; independently reviewed inputs/venue are still required before native execution. Expected input digest is supplied separately, not inside this object. The sourceRevision binds authored payload provenance without being a credential/configuration hash.

APPLIANCE_MANIFEST exact top-level fields: common fields above plus `kind: "APPLIANCE_MANIFEST"`, `inputsDigest`, `components` (the complete input artifact identity array), `outputs` (exactly `base`, `initramfs`, `kernel`, sorted by ID), `provenance`, `manifestSigning: "UNPERFORMED"`, `runtimeQualification: "UNPERFORMED"`. Output identity uses the same required fields; kernel/initramfs hash/size equal their corresponding input components. Base hash/size cover output bytes only. Output provenance has exact fields `sourceRevision`, `approvalId`, `buildEnvironmentId`, `assemblyMode: "SYNTHETIC"|"NATIVE_ARM64_LINUX"`, `tools` (same identities). Source/review/venue/tool facts are copied from the checked input, never inferred from output name. INCOMPLETE output is allowed as a synthetic assembly result but cannot be promoted to a qualified final appliance. Every M3 produced output has SYNTHETIC mode and UNPERFORMED signing/qualification, including complete synthetic fixtures.

Output directory production is exclusive/no overwrite. The driver uses a unique owned sibling partial directory and cleans up only that partial directory on failure. It must neither remove an existing destination nor clean sibling/historical paths. Future native output filenames are `readonly-base.raw`, `kernel`, `initramfs`, `manifest.json`, `provenance.json`; M3 fake output uses `base.synthetic`, `kernel.synthetic`, `initramfs.synthetic` and identity documents so fixtures are explicitly not real boot artifacts/images. Detached provenance records exact verified inputs/tool hashes, fixed argv, mode, and canonical input/output identities; the manifest does not digest that sidecar, avoiding a cycle. The sidecar can include manifestDigest after manifest serialization.

Archive admission is bounded and rejects traversal, absolute paths, escaping or ambiguous symlink/hardlink resolution, special device/FIFO/socket members, unexpected privilege/modes, forbidden runtime-secret material and unauthorized install locations. Never blindly extractall or delegate extraction to a shell. The future fixed image command is an explicit argv for the pinned mke2fs, using a task-owned populated directory and image destination; no shell, fetch, Docker, mounting, implicit install or host-private input. Only an injected fake may be invoked in M3. Real adapter source may exist but cannot be selected by a default, CLI path or import. Actual official input archive structure and final population remain construction gates.

## API contract, proof states and errors

Python in `assemble.py`:

* `decode_inputs(data: bytes) -> dict` and `decode_appliance(data: bytes) -> dict`: strict schema/semantics only.
* `canonical_manifest(value: dict) -> bytes` and `manifest_digest(value: dict) -> str`: validate first; use canonical boundaries above.
* `validate_inputs(manifest: dict, *, locations: Mapping[str, Path], tool_locations: Mapping[str, Path], expected_inputs_digest: str) -> ApprovedInputs`: immutable checked record of canonical input and captured matching bytes/metadata, fixed archive/kernel/runtime/policy validation; no execution and no authority from a bool. `ApprovedInputs` means input integrity/structure, not signature or operator approval. Direct arbitrary-record construction is unsupported; assembly revalidates its captured state.
* `assemble(inputs: ApprovedInputs, output: Path, *, image_tool: ImageToolRunner) -> dict`: runner argument required, no subprocess default. Runner receives a finite command record containing pinned tool identity, exact argv and owned staging paths; supplies a synthetic result in M3. Revalidate consumed inputs and tool identity, enforce exclusive outputs/owned cleanup, record output byte hashes/provenance and always leave qualification/signing UNPERFORMED. M3 does not provide an operational-approval constructor. CLI argument parsing may be authored; CLI assembly remains unavailable pending separate native venue/construction authority.

Swift in `VMConfiguration.swift`:

* `ApplianceManifest.decode(_ data: Data) throws -> ApplianceManifest`: immutable value, no public arbitrary initializer; schema and semantic validity only.
* `canonicalBytes() throws -> Data`, `digest: String` (computed SHA256 canonical output).
* `verifyArtifacts(locations: [String: URL], expectedManifestDigest: String) throws -> ArtifactVerifiedAppliance`: require all three outputs, exact identity and captured bytes/owned handle state; separate local location record. This checks output bytes and independent expected identity, not provenance truth, guest contents, trust or bootability. Future runtime admission also needs component/host identity observations.
* Configuration model/build uses ArtifactVerifiedAppliance and explicit owned serial handle boundary; pure planning/config-object inspection never creates a runtime admission proof. Existing planned `buildConfiguration(manifest:)` may be a method on this artifact-checked value or take it explicitly; raw decoded manifests must not authorize attachment/start.
* `runtimeBlockers` provides finite reasons; all M3 manifests have unavailable signing/qualification proof. Runtime VM start additionally needs nominal independently verified manifest signature, launcher signing/entitlement, release/run/broker-channel binding and later guest/terminal qualification. Missing future implementations close the gate. Fake lifecycle tests exercise a distinct injected effect boundary and cannot produce authority for a native adapter. No `verified: true`, `signed: true`, `qualified: true`, `allowSynthetic`, or equivalent caller switch enables native start.

Narrow M1 helper exposure, ownership fixed before source addition:

* Task7 `guest/protocol.py`: `decode_document(data, *, rule, definitions, max_bytes)` and `canonical_document(value, *, rule, definitions, max_bytes)` reuse `_pairs`, `_integer`, `_depth`, `_check`, existing canonical JSON rules. `_check` may accept explicit definitions with existing M1 defaults; receipt/frame APIs and semantics are unchanged. ## Implemented offline boundary and compatibility limits

`assemble.py` implements the pure validator and synthetic assembly driver. Its `ImageToolRunner.run(ImageCommand)` argument is mandatory; no subprocess/download/mount API, native runner, or real construction default is provided. The CLI currently returns exit78 without reading inputs or creating outputs. An `APPROVED_CANDIDATE` declaration is accepted for structural/input validation only and cannot execute this driver; only SYNTHETIC input can reach an injected runner. This restriction is deliberate until separate construction approval and a reviewed real adapter exist. `require_qualified` always rejects: incomplete payload, then synthetic mode, then unavailable signing. No native proof is manufactured.

The fixed modeled future argv is `(toolSnapshot, "-q", "-t", "ext4", "-b", "4096", "-d", populationPath, syntheticOutputPath, "262144")`. It describes a 1GiB initial build volume (262144 blocks of4096); this is unqualified construction sizing, unrelated to writable acceptance-run storage. M3 never creates populationPath, extracts a rootfs, or executes this argv. The injected test fake reads the checked tiny snapshots and writes explicitly nonbootable synthetic bytes; the driver recomputes their identities. Native Linux population, ownership preservation, filesystem reproducibility and bootability remain future adapter/qualification work. Synthetic input plus tool bytes and each output are capped at16MiB; manifest artifact identities allow up to64GiB for future inputs.

Input identities are captured with regular-file, no-symlink, single-link checks, hash/size and device/inode/mtime/ctime/mode metadata. Assembly rereads and hashes originals while copying to owned read-only snapshots, checks original and snapshot identities after the fake runner, and checks output identity before publication. `ApprovedInputs` has an internal constructor token and immutable captured records; it is an integrity record, not an adversarial Python sandbox. Caller code and injected effect implementations remain trusted process code. Runtime host attachment must separately solve retained native handle authority; these checks do not qualify native VM attachment.

Publication uses an exclusively allocated sibling partial directory followed by exclusive final-directory reservation. It links only the five known verified output/provenance/manifest files, with manifest last. No replacement of an existing destination is allowed. On a publication failure, cleanup is confined to a directory this invocation created and whose device/inode still matches; the originally reserved final directory is still considered this invocation's partial output until manifest publication completes. Cleanup does not follow a replacement symlink. Publication is not claimed to be an atomic whole-directory transaction; operational consumers need independent identity and proof checks and cannot treat a directory's presence as authority.

Archive validation permits only regular files, directories, resolved internal relative symlinks and internal hardlinks to regular files; every target must be present in that archive, and no member can have a link/non-directory ancestor. It rejects absolute links even when a future guest root could make them safe, unresolved links, setuid/setgid/sticky bits, group/world-writable regular files, device/FIFO/special members, duplicate entries, non-ASCII or ambiguous names, traversal and cycles. Maximum100000 members,64GiB declared expanded file bytes and4096-byte names apply. Official Ubuntu archives can contain absolute links, sticky directories or setuid members, so **raw upstream archive compatibility is not established**: a separately approved sanitized seed/layout or a reviewed narrow normalization rule is needed before native construction; do not weaken these rules automatically. Runtime archives install only inside their fixed role-specific subtree; rootfs may not populate `/opt/acceptance`. Required Node/Python/Chromium regular executable members are `bin/node`, `bin/python3`, and `chrome`.

Forbidden name components include `.env`, `.aws`, `.ssh`, private-key filenames, credential/session files and secrets directories; archive contents and direct authored payloads (bootstrap, controller, proxy, verifier and policy files) use the same bounded streaming check to reject recognizable `PRIVATE KEY-----` markers, including markers crossing read-chunk boundaries. Public certificate PEM files are allowed in both forms. This finite check does not detect arbitrary encoded secrets or prove the absence of unknown operational secrets; independently reviewed provenance and future admission remain necessary. It exports only finite error codes. Kernel prerequisites require exactly one built-in `=y` declaration and reject contradictory standard `# CONFIG_* is not set` declarations in either order; unrelated comments remain allowed. These checks use the supplied config, but signature/source approval and evidence that kernel/initramfs actually correspond are unperformed.

The Python helper extension preserves all existing M1 default definitions, frame ceilings, receipt semantics and canonical encodings. Appliance raw decoding uses only the trusted finite schema, with a schema-derived bounded type stage for stable semantic error classification, followed by full exact schema/policy enforcement before returning anything. Unknown fields, duplicate keys and ambiguous numbers remain failures. The schema itself is source-relative trusted build data; packaged immutable schema delivery is future work.

Offline tests live in `../tests/unit/appliance_test.py`; use the coordinator's fresh-output wrapper described in the M3 verification recipe, not a historical command or exchange destination. Complete Python regression, Swift producer/consumer composition, independent review and the coordinator's final fresh evidence remain distinct gates. No test count or runtime result is implied by this README.
