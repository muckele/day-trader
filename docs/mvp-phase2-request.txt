3. COMMON DURABLE ORDER LIFECYCLE
=================================

Unify Alpaca-backed execution paths sufficiently that manual, trade-plan,
research-originated, and RoboTrader orders share the same financial-integrity
invariants.

Every Alpaca-backed entry must:

1. Verify owner authorization.
2. Verify expected Alpaca paper account.
3. Verify paper-only release mode.
4. Validate instrument/order eligibility.
5. Fetch sufficiently fresh account/order context.
6. Run required risk and spending checks.
7. Persist an order intent.
8. Atomically reserve applicable spending capacity.
9. Assign and persist a stable unique `client_order_id`.
10. Submit once to Alpaca.
11. Persist acknowledgement or mark submission as uncertain.
12. Reconcile by broker identifiers/client_order_id.
13. Persist fills idempotently.
14. Release or finalize reservations according to documented state rules.
15. Emit durable audit and notification events.

The same logical intent must never produce a second broker order merely because:

* HTTP timed out
* process restarted
* database save failed after submission
* the user clicked twice
* reconciliation retried
* the broker response was lost

Use idempotency and uniqueness at the database level where appropriate.

4. UNCERTAIN BROKER SUBMISSION RECOVERY
=======================================

Implement the missing uncertainty handling for manual and other Alpaca-backed
paths, not just RoboTrader.

Required scenario:

1. App sends order with stable `client_order_id`.
2. Alpaca accepts it.
3. Client receives timeout/network failure before acknowledgement.
4. App records state as uncertain, NOT rejected.
5. App attempts lookup by `client_order_id`.
6. If found, bind the broker order to the existing intent.
7. If temporarily not found, do not immediately submit a replacement.
8. Reconciliation retries for an explicitly bounded uncertainty window.
9. Only after documented terminal evidence may the intent become safely retryable.

Add regression tests for this exact scenario.

Also test:

* broker 500 after accepting request
* database error after broker acknowledgement
* restart during uncertainty
* repeated reconciliation
* duplicate user request while uncertainty exists

At no point should these scenarios create two Alpaca orders for one logical intent.

5. ATOMIC DAILY / WEEKLY / MONTHLY SPENDING RESERVATIONS
========================================================

Implement enforceable spending budgets shared across manual and automated
entry paths.

Existing configuration includes:

* `dailyLimit`
* `weeklyLimit`
* `monthlyLimit`

These must become actual execution limits, not display/configuration-only fields.

Define/document:

* Timezone used for boundaries.
* Start/end of day.
* Start/end of week.
* Start/end of month.
* Meaning of 0/null/missing values.
* What qualifies as spending.
* How pending orders reserve capacity.
* How partial fills consume capacity.
* How canceled/rejected/expired orders release unused reservations.
* How uncertain orders remain conservatively reserved.
* How replacements transfer rather than duplicate reservations.
* Whether selling a position replenishes budget.

For MVP, selling must NOT replenish entry spending capacity for the same
day/week/month unless the existing product contract explicitly says otherwise.

Use atomic MongoDB operations or transactions appropriate to the existing
topology.

A check-then-write race is not acceptable.

Required concurrency test:

Two valid requests arrive simultaneously.
Their combined spending exceeds a limit.
Exactly one may reserve enough capacity if both cannot fit.
The other must fail safely before sending an Alpaca order.

Test this across:

* manual + manual
* Robo + Robo
* manual + Robo

Use cash-aware sizing and do not treat margin buying power as available cash
for this non-leveraged MVP.

6. PARTIAL FILLS AND PROTECTIVE ORDERS
======================================

Complete the protective-order lifecycle.

For automated stock entries:

* Protection must reflect actual filled quantity.
* Partial fills must not create oversized protective exits.
* Additional fills must update protection safely.
* Duplicate reconciliation must not create duplicate protection.
* A canceled remainder must leave protection appropriate for the filled position.
* Child-order rejection or absence must be visible and auditable.
* Additional automated risk should be blocked when existing required protection
  is missing or unresolved.
* Restart/reconciliation must be able to recover protection state.

Test at minimum:

A. Entry 10 shares:

* fills 4
* protection becomes valid for 4
* fills remaining 6
* protection becomes valid for total remaining position without duplicate exits

B. Entry 10:

* fills 4
* remaining 6 canceled
* protection remains valid for 4

C. Protection submission fails:

* position is flagged unprotected
* alert/audit is created
* no new automated exposure is allowed until appropriately resolved

D. Reconciliation runs twice:

* no duplicate protective order

E. Position quantity changes before protective reconciliation:

* app never creates an exit larger than the actual remaining position

Where Alpaca-native bracket behavior already handles a case correctly,
reuse it instead of reproducing broker logic unnecessarily.
