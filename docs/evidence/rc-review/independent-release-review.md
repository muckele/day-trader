## Confirmed blocker register and acceptance contract

### RC-001 — Emergency stop bypass at final broker account verification — P1 / RELEASE BLOCKER

The worker’s callback obtains account/positions/orders/clock, then asset metadata, then settings, performs risk evaluation, and finally awaits lease refresh (`worker.js:792–817`). The canonical lifecycle invokes that callback after claiming the persisted intent (`orderLifecycleService.js:94–96`) and calls `broker.submitOrder` (`:98`). The adapter awaits a separate `verifyPaperAccount` GET at `alpacaBroker.js:120`; after it returns, only readiness is rechecked before actual HTTP dispatch at `:122`. Emergency stop writes disabled settings at `worker.js:1045–1050` and looks for currently visible broker orders at `:1099`; the held request has no order for that scan to cancel.

The real-process/local-provider probe paused the seventh `/v2/account` GET, completed a separate emergency-stop process with0 POSTs, then released the GET. It observed1 new POST, `isEnabled=false`, and a new seven-share AAPL buy-limit order. This is a pre-POST control race, not a claim that accepted broker orders can be instantly undone. Current process.test.cjs “immediately before” tests pause at asset requests, which precede the final callback and therefore miss this later wait.

Affected proven path: current Robo automated entry via scheduler or owner Run Once -> worker -> canonical submit -> createAlpacaBroker. Same structural late adapter wait is shared by canonical manual submissions and lease-protected reducing/protective mutations, but automated disable is not currently defined to ban deliberate manual entries. Do not silently change that policy or block protective sells. The analogous protection/close stale-lease mutation and final-account lease-takeover variant are risks to test, not separately reproduced findings.

Correction acceptance must define three separate events: (S) durable stop/control-generation transition; (D) durable final dispatch claim tied to the existing intent, account, payload, current generation and worker lease; (T) actual transport dispatch, which is not the same as broker acceptance. D must occur only after asynchronous provider preflight and be serialized with S/lease ownership. If S wins, later D must fail and produce zero POSTs. If D wins, stop must list the exact existing client identity as potentially in flight until the claimant is proven unable to send, or an actual attempt is reconciled. Do not relabel the current earlier `submitting` state as proof that T occurred.

A final callback after account verification closes the demonstrated wait, but alone leaves a read/check/use race with another process and may itself await lease renewal after reading settings. A plain Mongo lease token is not broker-enforced fencing: a suspended process may resume after takeover. Preserve pending/quiescing stop state when a prior claimant cannot be conclusively drained; do not report completed quiescence merely because a timer expired or a lookup returned404. If stronger physical no-send-after-stop-completion semantics are offered, stop completion must wait for dispatch drain/claimant acknowledgment or a proven exclusive dispatch boundary. No finite sequence of independent reads establishes atomicity with an external network send. Unknown state stays explicit and reserves exposure. No write POST/PATCH/DELETE belongs inside a retryable transaction callback.
