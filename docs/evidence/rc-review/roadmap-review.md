## Canonical lifecycle and model ownership

- `OrderIntent` owns durable logical action, account/environment/source, stable idempotency/client identity, payload fingerprint, lifecycle status, reservation and cumulative filled amounts (`backend/models/OrderIntent.js:24–27`, unique account/environment/key index `:37`).
- `BrokerOrder` owns broker acknowledgement/order-state and replacement linkage beneath the intent (`backend/models/BrokerOrder.js:7–17`, unique account/external order index `:33`).
- `Fill` owns incremental broker-confirmed fill accounting, linked to both intent and broker order (`backend/models/Fill.js:5–15`, cumulative-quantity uniqueness `:29`). Canonical `orderLifecycleService.js:102–127` ingests cumulative broker reports transactionally, creates only positive deltas, updates reservations/spending and emits audit/outbox events. Reconciliation at `:132–139` polls durable broker/client identities rather than resubmitting.
- `RoboTradeDecision` owns decision/rationale/research/checks/rejections, not the execution ledger (`backend/models/RoboTradeDecision.js:19–41`). Its existing flexible Mixed fields and status vocabulary do not yet implement the strict versioned proposal contract.
- `RoboTradeOrder` is a Robo UI/compatibility projection linked to intent/decision, not another source of fill or reservation truth (`backend/models/RoboTradeOrder.js:18–24`). `backend/robotrader/worker.js:584–604` calls canonical lifecycle first, then writes this projection; its explicit comment at :594 establishes ownership. `backend/robotrader/reconciliation.js:19–38` reconciles shared intents including manual entries, then refreshes projections. Legacy rows without intent identity are insufficient protection-write authority (`reconciliation.js:6–9`).
- `OrderProtection`, `PositionClose`, `AccountCapacity`, `SpendingBucket`, account leases, `RoboAuditLog` and `NotificationOutbox` remain the existing operational state owners. Agent proposals must not create a second order/position ledger or mutate these directly.
- Broker positions/history are external observations, while canonical fills describe app-owned confirmed execution (`alpacaPortfolioService.js:16–37`). RC002 must resolve disagreement conservatively; neither a stale empty positions response nor a compatibility projection should erase known filled exposure.
