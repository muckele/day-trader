## Application/runtime inspection

The reviewed backend package manifest has ten direct dependencies: axios, bcryptjs, cors, dotenv, express, jsonwebtoken, mongoose, nodemailer, and openai. Parsing every `packages` entry of `backend/package-lock.json` found no `hasInstallScript`, OS, or CPU restrictions. The current local dependency tree contained no `*.node` addon files. This is evidence for the current graph; the final Linux production tree still needs independent inspection after installation.

A bounded search of production JavaScript excluding tests, integration harnesses, scripts, and node_modules found no child_process calls or explicit fs read/write imports/calls. This is not a proof about every dependency feature. The bcrypt dependency is bcryptjs. Nodemailer is configured for SMTP with TLS, not its optional sendmail subprocess transport (`backend/services/roboEmail.js`). The shell restart helper and integration openssl/git/subprocess callers belong to host/test operations, not `node server.js` startup.

`backend/utils/marketStatus.js` uses `Intl.DateTimeFormat` with `America/New_York`; winter/summer DST behavior is a runtime requirement. Preserve the exact Node binary's ICU data and retain supported tzdata. Mongo and HTTP/SMTP clients require DNS and trust facilities. Node's embedded CA set and optional system CA behavior are separate; preserve the Debian CA bundle and hashed certificate links rather than assuming embedded roots cover every deployment mode.

Historical exact-image evidence (`../../image-scan/authenticated-retry/local-exposure-checks.json`) shows the previous arm64 Node binary linked only libdl, libstdc++, libm, libgcc_s, libpthread, libc, and the glibc loader. It did not dynamically link OS zlib, PCRE2, or ICU. This historical evidence supports the design investigation, but does not replace candidate inspection. Removing Debian libz does not remove Node's compiled-in zlib; record `process.versions` and assess any Node-bundled finding independently.

## Recommended bounded construction and maintenance conditions

A final scratch filesystem assembled from the approved Node Bookworm stage is a Debian-derived runtime, with upstream Debian libraries and the unmodified official Node binary. It is an application-maintained assembly, not a separately vendor-supported preassembled Debian image. It preserves the existing libc family and avoids adding musl compatibility uncertainty. A maintained distroless Debian base may reduce assembly maintenance later, but its exact Debian release, Node version, dependencies, and digests require a separate comparison before replacing this bounded path.

1. Keep the pinned official Node 24.21.0 Bookworm image as the installation/assembly provenance. Refresh its Bookworm package indexes and apply supported security updates before exporting runtime content. Capture actual selected package versions and repository configuration. Final rebuilds are the update mechanism; package managers are unnecessary after startup.
2. Export a documented allowlist of runtime library/package files: libc6 libraries and architecture-specific loader, libgcc-s1 and libstdc++6 libraries, CA certificates and generated trust links/bundle, timezone data, and essential configuration. Include NSS/dlopen support instead of assuming `ldd node` exhausts runtime dependencies. Preserve symlink targets and resolve all architecture-specific paths from the target image.
3. Preserve `/etc/os-release` (and its target), `/etc/nsswitch.conf`, minimal passwd/group entries, a usable working/home directory where needed, and `/tmp` with mode 1777. Docker provides `/etc/hosts`, `/etc/resolv.conf`, and hostname at runtime; do not bake the builder's resolver into the image. Use an exec-form Node command and Node or external health probes. Do not depend on `/bin/sh`, npm, npx, corepack, Perl, mount, or nsenter.
4. Retain Debian copyright/license files and Node LICENSE, provenance package records, and a path/owner/hash manifest for actual selected files. If a package record covers an exported subset, document that fact; do not imply every file or maintainer script from the full package is installed. Metadata removal is not vulnerability remediation. Scanner-visible source/version attribution must remain truthful for libc and compiler runtime libraries.
5. Install production dependencies using the unchanged lockfile and preserve their package metadata. Copy a deliberate application allowlist; exclude test/integration sources, operational tooling, registry configuration, credentials, and env files. Future dependency updates must recheck native addons, install scripts, subprocess dependencies, and new dynamic links.
6. Require final-image checks for Node version/embedded components, shared-library closure and expected omissions, DNS including local service names, Mongo readiness/index/write operations, TLS trust, New York winter/summer timezone results, nonroot permissions, truthful health semantics, and signal shutdown. Debugging changes operationally because no shell/package manager exists; use Node entrypoints, external probes, and disposable debug containers. No external brokerage, SMTP send, or inference is necessary for these checks.

The principal maintenance risk is drift in the exported filesystem as Node, Debian packages, or npm dependencies change. A checked export manifest, failing dependency/absence assertions, fresh package updates, and exact-image acceptance are required to make this design defensible. It must not be selected merely because omission of metadata reduces scanner counts. [Node's platform documentation](https://github.com/nodejs/node/blob/main/BUILDING.md) makes libc/platform support relevant, and [Debian LTS](https://www.debian.org/lts/) provides the distribution support context; neither source certifies this custom assembly's application behavior.
