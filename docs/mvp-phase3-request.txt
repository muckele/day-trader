===================================

============================================================
9. COORDINATED MANUAL EXIT WORKFLOW
===================================

Resolve the remaining Phase 2 limitation where an existing protective
reservation/order can conflict with a manual position close.

Implement a safe coordinated close workflow.

The owner should be able to intentionally close an Alpaca-paper position
without creating duplicate or oversized exits.

Required sequence should safely coordinate:

* existing protective order discovery
* cancellation request where appropriate
* confirmation or uncertain-cancel state
* actual remaining position quantity
* close submission
* reconciliation

Do not:

* send a full close while a full-size protective exit can still independently
  execute
* assume cancellation succeeded because a DELETE request returned
* cancel unrelated broker orders
* silently leave the position unprotected for an unbounded period

If cancellation state is uncertain, fail safely and surface the condition.

Add browser + backend regression coverage.

============================================================
10. CASH RESYNCHRONIZATION
==========================

Address the documented conservative Phase 2 behavior around available cash.

Do not simply add sale proceeds immediately from local assumptions.

Design a safe resynchronization rule using confirmed broker/account state.

Requirements:

* spending-period usage remains historically consumed
* selling does NOT reset day/week/month spending budgets
* confirmed account cash can refresh the separate cash-capacity constraint
* deposits/withdrawals are recognized only from trustworthy broker state
* an unknown/stale account state fails closed for new entries
* synchronization cannot double-credit sale proceeds
* concurrent resynchronization and reservations remain safe

Clearly separate:

A. period spending budget
B. current broker cash available for non-leveraged purchases

Add real Mongo concurrency tests.

============================================================
11. IDENTICAL ORDER USER INTENT
===============================

Resolve the browser behavior where an identical payload may retain its
session request key.

The system needs to distinguish:

A. accidental duplicate/retry of the SAME user intent

from:

B. a deliberate NEW order with identical economic parameters.

Design an explicit UI/request-intent mechanism.

A deliberate second identical order must require a new explicit user action
after the prior logical request is visibly resolved or otherwise safely
distinguished.

Do not solve this by making every click generate a fresh idempotency key;
that would defeat duplicate-click protection.

Add Playwright coverage for:

* double-click same action → one logical/broker order
* retry after ambiguous response → same logical order
* deliberate second identical order after appropriate user action →
  new logical order and new client_order_id
